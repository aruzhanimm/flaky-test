Локальный протокол до обучения моделей
Дата 13 октября 2026. Это датированный рабочий протокол, не публичная preregistration.
Данные и форматы диагностики уже изучались. Предсказания и метрики модели на момент записи протокола не получены.

Постановка
RQ, aim, пять objectives и двусторонние H0/H1 из актуального A2 сохраняются.
Delta = masked macro-F1 minus original macro-F1.
Исследование является сравнением представлений диагностики в наблюдательном корпусе. Оно не доказывает механизм flaky-поведения или причинную вредность идентификаторов.

Единица и доступ
Одна основная запись соответствует одному canonical project+test. Сначала для каждой авторской записи выбирается первый доступный подтверждённый target failure в порядке recorded iteration, затем source CSV row. Для NIO используется точный target result из вложенного JSON. Для Surefire выбирается XML этого запуска, иначе TXT того же test class. Имена, пути архива, labels и summary не являются входом основного классификатора.
Варианты одного теста объединяются. При нескольких пригодных вариантах выбирается iDoFT перед JIRA, далее container в лексикографическом порядке. Это детерминированный отбор, а не установление хронологически первой revision.
Архивные логи анализируются как опубликованные авторами. Мы не утверждаем, что заново выполнили Java-тесты или Docker reproduction.
Строки без подтверждённого падения, пустой диагностики, точного target, известного supervised label или проверяемой группы репозитория не входят в модель. Пустой revision не заполняется догадкой: такие записи исключаются из основного набора и перечисляются отдельно. CURATOR-671 имеет подозрительный SHA, общий с другим проектом; до независимой проверки он исключается по неопределённости revision, а не по результату модели.
UNCLASSIFIED не получает выдуманную метку. Неудача HTTP-загрузки отличается от отсутствия или непригодности данных. До основного запуска должны быть завершены попытки получения и сохранены причины всех исключений; технические пробелы явно ограничивают доступную популяцию.
Флаги class-initialization и missing-class не ведут к автоматическому исключению: подобная ошибка может быть следствием order dependence. Они используются для ручного разбора и отдельной чувствительности, если доказана альтернативная причина.

Группы и повторения
Группы проекта используют публичный GitHub repository_network_root_id, проверенный с сохранением исходных страниц и SHA256. Это объединяет переименования и известные GitHub forks; не доказывает отсутствие общих библиотек, скопированного кода или независимых mirrors.
Точное совпадение исходной общей диагностической строки между разными группами проверяется до обучения. В основной выборке оставляется запись с первым canonical_test_id в лексикографическом порядке; остальные перечисляются как exact_cross_project_duplicate. Внутри проекта разные тесты сохраняются, но все находятся в одной группе. Похожие шаблоны ошибок проверяются отдельно; их сходство не объявляется автоматически утечкой.

Категории
Основная оценка планируется для ID, OD, NIO, TD, если каждая категория после аудита остаётся хотя бы в трёх группах проектов. Иначе неподдержанная категория исключается до модели и описывается отдельно. Изменение фиксируется как отклонение протокола с причинами и без обращения к model scores.
NIO имеет особенно слабое независимое покрытие: почти все записи происходят из junit-quickcheck, вне него лишь несколько тестов. Поэтому отдельно выполняется заранее заданная чувствительность ID/OD/TD. Число повторов NIO не компенсирует это ограничение. Основные и вспомогательные результаты не смешиваются.

Общая подготовка
Используется только exception type, message и body stack trace, реально присутствующие в отчёте. XML properties, stdout соседних тестов, Maven build headers, durations, summary и классификационные labels не включаются. Одинаково в обоих условиях нормализуются line endings, удаляются ANSI escape sequences и завершающие пробелы. Строки stack frames инструментов NonDex, iDFlakies/testrunner, Maven Surefire и JaCoCo удаляются в обоих условиях, чтобы уменьшить непосредственные признаки сборщика. Остальные framework frames и численные значения сохраняются.
Поля XML и TXT приводятся к одинаковой структуре. NIO JSON может не содержать exception type/message; отсутствие не восстанавливается по метке и не заменяется выдуманной exception.

Маскирование
Правила не обучаются на labels или evaluation scores. Используются явные project/test identifiers из metadata данного примера и проверенное имя репозитория.
1. Полные exception class names, в том числе chained causes, сохраняются дословно.
2. Полное имя test class и его простое имя заменяются TEST_CLASS; квалифицированное target method заменяется TEST_METHOD.
3. Длинные самостоятельные target method names маскируются по границам токена; короткие неоднозначные имена маскируются только рядом с именем класса. Это явное ограничение охвата.
4. Имена репозитория и негeneric компоненты его названия заменяются PROJECT при совпадении границ идентификатора, без удаления всех символов организации Apache/Google и т.п.
5. Пути с такими project/test identifiers заменяются PROJECT_PATH, сохраняя окружающую структуру сообщения.
Placeholders одинаковы во всех проектах. Маскирование частичное: production class/method names и неизвестные aliases могут сохранять проектную информацию. Их наличие проверяется и обсуждается, а не объявляется полная анонимизация.

Обучение и оценка
Leave-one-project-group-out. Каждый пригодный тест оценивается один раз; весь удержанный проект исключён из обучения. Метки и sample IDs одинаковы в original/masked.
Новый fitted TF-IDF и новый LogisticRegression для каждого fold и условия. TF-IDF word unigrams/bigrams, lowercase, token pattern (?u)\b\w\w+\b, min_df=1, max_features=30000, sublinear_tf=true, L2 normalization. Logistic regression C=1, solver=lbfgs, max_iter=2000, class_weight=balanced, random_state=20261013. Настройка гиперпараметров по held-out результатам не проводится. Параметры фиксируются в config JSON.
Class labels проверяются в training portion каждого fold. При исчезновении категории оценка этого дизайна останавливается и причина исправляется до получения итоговых метрик. Состояние fitted моделей и векторизаторов между folds/conditions не переиспользуется.
CPU, один вычислительный поток для повторяемости. Версии и команды сохраняются. Повторный независимый запуск должен дать те же predictions и метрики в пределах указанной численной точности.

Метрики и estimand
Основной project score: macro-F1 по категориям, фактически представленным в истинных метках данного удержанного проекта; labels задаются явно одинаково для двух условий, zero_division=0. Непредсказанные представленные категории получают 0. Отсутствующие истинные категории не добавляются как фиктивные нулевые классы. Сохраняются число и состав категорий каждого проекта.
Основной estimand: невзвешенное среднее paired delta по удержанным проектам, соответствующее формулировке H0/H1. Проекты с одной категорией распространены, поэтому эта величина не заменяет общую оценку по четырём категориям.
Обязательно вместе с ней: pooled out-of-project macro-F1 с фиксированными всеми eligible labels, per-category precision/recall/F1/support, confusion matrices и per-project scores. Accuracy лишь дополнительная.
Majority baseline обучается только на training labels. Диагностическая baseline использует только формат/инструмент источника, чтобы показать category-tool confounding; это не основной log classifier. Её признаки не передаются original/masked моделям.

Неопределённость и выводы
Показываются все project deltas, медиана и среднее. 5000 bootstrap resamples по целым project score pairs с seed 20261013 дают описательный 95% interval условно на уже полученных predictions. Из-за пересекающихся training folds и малочисленных независимых проектов редких категорий это не строгий доверительный интервал для всех будущих Java проектов. Не выполняется t-test по строкам логов и не заявляется доказательство H0 при отсутствии различия. Формальный причинный вывод или универсальное отклонение H0 не делается только на основании этого exploratory interval.

Ошибка и воспроизводимость
Сохраняются predictions с canonical test/group IDs, полные confusion matrices, результаты checks, hashes входов/config/code, stdout и время обучения. Отдельно экспортируются все changed predictions и числа улучшений/ухудшений; примеры обоих направлений выбираются детерминированно, без показа только удачных.
Изменения parser, маскирования, eligibility или модели после просмотра scores получают новую версию протокола и объяснение. Исправление подтверждённого бага требует повторения затронутой оценки. Ни одно неудобное наблюдение не удаляется ради роста метрики.


Поправка v2 после первого пилота, до окончательного корпуса и основного анализа
Первый пилот v1 и повтор сохранены без изменений. На его 435 тестах оба условия дали pooled macro-F1 0.5822096365; два предсказания поменялись в противоположных направлениях. Следовательно, поправка сделана после ознакомления с этими результатами и не является слепой preregistration.
При чтении реального NIO-примера quickcheckc1c1 обнаружено, что компонент junit из имени junit-quickcheck заменялся в общем пакете org.junit. Это выходит за предполагаемое маскирование идентичности проекта и затрагивает общий тестовый фреймворк. В список generic-компонентов добавлены junit, testng, hamcrest, mockito, jupiter. Полные имена проекта и собственные имена тестов маскируются по прежним правилам. Исключения по-прежнему сохраняются. Изменение не выбиралось по росту метрик. Другие правила, состав пилота, модель, разбиения, метрики и запланированная чувствительность остаются прежними.
Пилот v2 использует ровно те же 435 sample IDs, метки и исходные тексты; пересоздаётся только masked_text. Версии v1/v2 и hashes хранятся отдельно. Основной полный анализ использует v2. Результаты оцениваются как исследовательские с явным сообщением этой поправки.


Поправка v3: подтверждённая форма имён JUnit 5, до итогового обучения
После просмотра пилотов v1/v2 и при продолжении аудита обнаружен реальный отчёт ignite3modulesstoragerocksdb19c8a82testScanOverEmpty: metadata target testScanOverEmpty, XML name testScanOverEmpty(ScanTimestampProvider)[1] и [2], classname совпадает точно. Старый parser поддерживал суффикс [case], но не явную сигнатуру (Type)[case]. Это ошибка охвата формата, а не основание считать, что target отсутствует.
Версия 3 принимает имя method(JavaType,...)[case] либо method() при точном совпадении classname и имени метода. Произвольный prefix и display-name mapping запрещены; несколько различных сигнатур одного target в одном XML считаются неоднозначными и требуют разбора. Повторно проверяются уже скачанные попытки в исходном порядке, без обращения к предсказаниям. Class-level failures с name равным classname, как в hippo4jinfracommonee2a81fbuildUrl, не приписываются target method.
Состав итогового корпуса ещё не заморожен и итоговые модели ещё не обучены. Поправка сделана после доступа к пилотным scores, что раскрывается. Исходные пилотные snapshots не заменяются. Правила маскирования остаются v2, модель и метрики прежними. Итоговые запуски называются main_v3 и ссылаются на этот протокол. Изменения локальных записей сохраняются в evidence/parser_v3_reparse.json.
